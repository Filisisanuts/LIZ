# Ax-Coffee 前端工程化重构方案

> 状态：已确认方案，待实施
>
> 更新日期：2026-09-14
>
> 范围：`project-002-ax-coffee` 的前端架构、样式体系、测试、报表分享与 Linux 服务器部署。

## 1. 重构目标

在不改变现有经营业务含义、Supabase 数据归属与老板报表可见范围的前提下，将当前由静态 HTML、全局 JavaScript 和单一 CSS 文件构成的系统，渐进重构为可构建、可测试、可维护、可部署到自有 Linux 服务器的前端工程。

### 达成标准

- 新前端使用 **Vite + 原生 JavaScript ES Modules**；新模块默认使用 TypeScript。
- 旧功能在本地以新旧并行方式逐模块迁移，最终只部署一次已完整验收的版本。
- 样式从单一全局文件与内联样式，改为设计令牌、基础样式、组件样式与功能域样式的分层结构。
- 主经营系统仍由浏览器直连 Supabase；随机分享报表改由服务器 API 鉴权后提供。
- 正式站点改由 Linux 服务器的 Nginx 托管，不再依赖 GitHub Pages。
- 任一模块上线前均通过类型、业务逻辑、真实浏览器行为与视觉回归四层验收。

### 不在本期内做的事

- 不一次性重写为 React、Vue 或其他完整 UI 框架。
- 不改变日报、采购、费用、库存、结转、退货、AI 识别等既有业务规则，除非另行确认。
- 不将全部主系统数据访问迁移到自有后端。
- 不在工程化迁移中大幅改版视觉风格；第一期保持米白、金棕的咖啡经营台账风格，仅改善一致性、可访问性与响应式体验。

## 2. 已确认的架构决策

| 主题 | 确认结论 |
| --- | --- |
| 前端技术栈 | Vite + 原生 ES Modules |
| 类型策略 | 新代码使用 TypeScript；遗留 JavaScript 渐进迁移或补 JSDoc |
| 迁移方式 | 本地新旧并行、按功能域替换、每模块独立验收 |
| 最终发布 | 本地完整验收后一次性部署到 Linux 服务器 |
| 静态托管 | Nginx 托管 Vite 产物 `dist/` |
| 主系统数据访问 | 浏览器继续使用 Supabase Auth 与数据访问 |
| 分享报表 | 长期高熵随机链接、可撤销/重生成；服务器 API 校验令牌 |
| 报表内容 | 分享链接可查看当前已确认的完整经营报表，不额外隐藏字段 |
| 移动端重点 | 优化图表、报表 Tab、表格溢出、空状态与长数据布局 |
| 自动部署 | 第一阶段不强制引入；先以本地验收后手动、可回滚部署为准 |

## 3. 现状与重构动因

当前项目是无构建步骤的静态站点：`index.html` 通过严格顺序加载多个全局 JS 文件，`src/css/style.css` 承担大部分样式职责，业务模块通过字符串拼接 HTML、内联样式与全局事件函数完成交互。

以下文件已达到高维护风险规模：

| 文件 | 行数 | 函数数 | 主要职责 |
| --- | ---: | ---: | --- |
| `src/js/purchase.js` | 2,383 | 75 | 采购、AI 识别、退货、日历、库存联动 |
| `src/js/inventory.js` | 2,167 | 54 | 贵重库存、入出库、销售、结转、兑换 |
| `src/js/daily.js` | 1,818 | 41 | 日报、客情、日历、校验 |
| `src/js/report.js` | 1,165 | 16 | 报表计算、数据表与图表 |

当前实现可继续使用，但存在以下维护问题：

1. 同一文件混合数据计算、DOM 拼接、内联样式、事件绑定、弹窗流程与同步逻辑，局部改动难以隔离。
2. 多个脚本依赖全局变量和固定加载顺序；导航配置也存在重复来源，容易发生修改遗漏。
3. CSS 缓存版本在不同 HTML 页面中不一致，移动浏览器可能继续使用旧资源。
4. 部分移动端和可访问性问题需要修复，例如禁止页面缩放、非语义化点击元素、Modal 焦点管理不足、Toast 未提供读屏提示。
5. 公开报表当前不能仅依靠页面路径保护；随机分享链接必须由服务器验证，不能继续让浏览器直接读取公开共享数据。

### 4.1 目录标准化原则

目录标准化属于第 0 阶段，但不得通过一次性移动现有运行文件完成。当前站点依赖根目录 HTML、相对资源路径和经典脚本加载顺序；在 Vite 兼容骨架完成前移动这些文件，会直接破坏旧站点。

执行顺序固定为：

```text
新增规范目录与文档
  → 保留旧目录和旧入口作为兼容实现
  → 按功能域迁移到新目录
  → 完成新旧对照验收
  → 仅在旧入口不再被引用后归档或删除遗留文件
```

项目根目录只保留构建入口、工程配置和项目说明。Vite 的 `index.html` 作为构建入口可以继续位于根目录；这属于 Vite 的标准约定，不应为了形式统一而移入 `src/`。

### 4.2 现有文件与目录去向

| 当前内容 | 迁移期间处理 | 最终去向或状态 |
| --- | --- | --- |
| 根目录 `index.html` | 保留为旧入口；再替换为 Vite 入口 | 根目录 Vite 构建入口 |
| 根目录 `login.html` | 保留，保证旧登录流程可用 | 合并为主应用登录路由，或作为 Vite 多页面入口 |
| 根目录 `dashboard.html` | 保留，继续作为旧只读报表对照 | 替换为受随机分享链接保护的报表路由 |
| `src/js/` | 原样保留，禁止全量移动 | 逐模块迁入 `src/features/`、`src/ui/`、`src/shared/`；完成验收后删除遗留实现 |
| `src/css/style.css` | 作为 `legacy.css` 的来源和视觉基准 | 拆入 `tokens.css`、`base.css`、`layout.css`、`components/` 与 `features/` |
| `config/` | 保留现有非敏感配置 | 增加 Nginx、systemd 等服务器模板，真实密钥仅放服务器环境变量 |
| `tests/` | 保留既有测试 | 扩充为 `fixtures/`、`unit/`、`integration/`、`e2e/`、`visual/` |
| 根目录 `test_screenshot.png` | 不在第 0 阶段移动，先核对引用关系 | 移入 `tests/visual/baselines/` 或删除；删除前必须确认 |
| `CNAME`、`CNAME.txt` | 迁移至自有服务器前保留 | 域名切换、HTTPS 和回退演练通过后归档或删除；删除前必须确认 |
| `docs/` | 保留已有测试文档和重构方案 | 补齐技术规范、开发日志、UI 组件规范、发布与回滚手册、分享报表安全设计 |
| `logs/`、`_temp/` | 保持项目内临时/日志边界 | 不提交；按任务产生和清理 |

### 4.3 目录变更验收

任何移动、归档或删除前，必须完成以下检查：

1. 搜索项目内对目标路径的 HTML、JS、CSS、测试和部署脚本引用。
2. 在旧入口和新入口分别验证页面加载、资源请求和主要交互。
3. 确认 Git 跟踪状态，避免将 `.env`、`dist/`、临时文件或真实经营数据一起暂存。
4. 对删除或弃用的内容先记录替代位置、回滚方式和最后一次验证结果；未经确认不得删除。

## 5. 新旧并行迁移机制

重构初期不删除遗留页面和功能。原有脚本将以兼容方式保留，新模块只通过有限的桥接层访问既有能力：

```ts
legacyBridge.getDatabase()
legacyBridge.saveDatabase(nextDb)
legacyBridge.openLegacyPurchaseEditor()
legacyBridge.refreshLegacyPage('purchase')
```

新模块不得再直接读写 `window.DB`，也不得继续自由调用全局函数。每个功能域的迁移路径如下：

```text
旧功能文件
  → 数据类型 types
  → Repository（读取/写入）
  → Service（业务计算）
  → 页面与局部 UI 组件
  → 新旧结果对照
  → 旧文件缩减为兼容入口
  → 删除遗留实现
```

## 6. CSS 与 UI 组件体系

### 6.1 样式分层

| 层级 | 职责 |
| --- | --- |
| `tokens.css` | 颜色、字体、间距、圆角、阴影、断点等设计令牌 |
| `base.css` | 重置、基础排版、焦点、深色模式、无障碍默认值 |
| `layout.css` | 应用壳、导航、页面容器、栅格和响应式规则 |
| `components/` | Button、Modal、Toast、Table、Tabs、FormField 等复用组件 |
| `features/` | 仅属于采购、库存、报表等某个功能域的样式 |
| `legacy.css` | 临时承接旧样式，随迁移逐步删除 |

### 6.2 UI 组件准入规则

满足任一条件必须抽为可复用组件：

- 将在两个或以上页面使用；
- 同一结构或样式复制两次；
- 单块渲染结构超过约 80 行；
- 需要处理焦点、键盘、异步、错误或加载状态；
- 属于 Button、Modal、Toast、表格、Tab、表单字段、日期选择器等基础能力。

新组件统一使用 `ax-` 前缀，例如 `.ax-button`、`.ax-modal`，避免和过渡期 `.btn`、`.card` 等遗留类名混淆。

### 6.3 强制样式规则

- 新代码禁止新增内联 `style`；动态视觉值使用 CSS 变量。
- 禁止 `transition: all`，必须列出实际过渡属性。
- 每项动画必须提供 `prefers-reduced-motion` 降级。
- 新增交互元素必须具有 `:focus-visible` 可见焦点。
- 新增图片提供替代文本、尺寸与懒加载策略。
- 不再人工维护 `?v=2` 一类缓存参数；使用 Vite 内容哈希产物。

## 7. 业务模块拆分边界

每个功能域按以下职责拆分：

```text
页面层：组合结构、响应路由、发起动作
UI 层：渲染组件和交互反馈，不包含业务规则
Service：金额、库存、结转、汇总等可测试业务逻辑
Repository：localStorage / Supabase 读取与写入
```

建议迁移顺序：

1. 应用壳、路由、通用 Modal、Toast、日期选择器、格式化工具。
2. Dashboard 与 Report：优先迁移只读页面，建立新表格、图表、URL 状态与手机布局基线。
3. Damage、Warehouse、Expense：验证表单、照片、编辑、删除、取消与数据 Repository。
4. Daily：迁移日报、客情、日历和数据校验。
5. Purchase：先迁数据模型和手动录入，再迁 AI 单据识别、退货、日历、库存联动。
6. Inventory：最后迁移入出库、销售、结转、兑换等高风险流程。
7. Settings、Sync、Auth：完成新配置与数据访问层收敛，清理遗留全局状态。

## 8. 手机报表优化

分享报表显示当前已确认的完整经营数据。第一期优化不改变指标与计算方式，重点改善呈现。

固定验收视口：

| 视口 | 用途 |
| --- | --- |
| 375 × 667 | 手机基线 |
| 390 × 844 | 常见手机 |
| 768 × 1024 | 平板 |
| 1280 × 800 | 笔记本 |
| 1440 × 900 | 桌面 |

优化项：

- 手机端将“表格 + 图表”由并列切换为纵向，优先显示摘要与趋势图。
- Chart.js 图表根据容器重绘，限制最小高度、标签字号和图例位置。
- Tab 支持横向滑动，当前报表 Tab、月份和筛选写入 URL。
- 长表格保留横向滚动，并提供明显的可滑动提示。
- 统一金额、日期、数字列对齐和等宽数字字体。
- 明确空数据、加载、错误、长文本和深色模式状态。

## 9. 随机分享报表安全设计

分享链接形态：

```text
https://<正式域名>/report/<高熵随机令牌>
```

访问链路：

```text
浏览器
  → GET /api/share-report/<token>
  → 服务器计算令牌哈希并校验有效性
  → 服务器读取 Supabase 的报表数据
  → 返回只读报表 DTO
```

分享链接记录至少包含：

```text
id
token_hash
label
created_at
revoked_at
last_accessed_at
```

管理端能力：生成、复制、撤销、重生成、查看创建时间与最近访问时间。第一期不强制密码，但预留按链接启用密码的能力。

> 安全要求：上线前必须关闭旧的“浏览器可直接读取公开共享报表数据”的路径。随机链接必须在服务端校验，否则只隐藏页面地址而不真正保护数据。

## 10. 开发、构建与 Linux 部署

本地开发命令（实施后提供）：

```text
npm run dev        # Vite 开发服务
npm run check      # 类型、Lint、单元测试
npm run test:e2e   # 浏览器真实行为测试
npm run build      # 生成 dist/
npm run preview    # 用生产产物本地验收
```

Linux 服务器部署：

```text
本地完成验收的 dist/
  → 上传到 /var/www/ax-coffee/releases/<版本>/web/
  → 原子切换 /var/www/ax-coffee/current 软链接
  → Nginx reload
  → 正式域名验收
```

服务器保留上一版 release；异常时仅回指 `current` 并 reload Nginx，不在线上临时改源码。

分享 API 是独立服务，使用 `systemd` 守护，Nginx 反代 `/api/`。静态前端无需 PM2 或长期运行 Node；仅分享 API 需要 Node 运行时。

跨平台要求：

- 导入路径统一使用 `/`，严禁 Windows 绝对路径。
- 导入文件名必须与真实文件名严格同大小写，以兼容 Linux 文件系统。
- `.gitattributes` 统一源码换行符；Linux 脚本只使用 LF。
- 本地 PowerShell 检查脚本与 Linux Shell 部署脚本分离。
- 浏览器公开配置使用 `VITE_` 环境变量；服务端密钥仅保存在服务器环境变量中，禁止进入 `dist/` 或 Git。

## 11. 强制开发规范

1. 修改前必须确认目标文件职责、行数、依赖关系与现有测试。超过 500 行的文件不允许继续无边界堆功能。
2. 新页面建议不超过 300 行；超过 500 行必须拆分，或在审查记录中说明不可拆原因。
3. 新代码默认 TypeScript；遗留 JavaScript 在迁移时至少补 JSDoc，并通过类型检查。
4. 新代码禁止新增全局函数、全局可变状态、HTML 内联 `onclick`、可点击的 `div/span`，以及未转义的用户数据 `innerHTML`。
5. 交互使用语义化 `button`、`a`、`label`、`table` 等 HTML 元素；键盘、焦点、读屏提示与触屏状态必须同时考虑。
6. 可分享或刷新后需恢复的页面状态必须进入 URL，例如页面、Tab、月份、筛选和展开状态。
7. 新依赖安装前必须进行安全与许可证审查、锁定版本并记录用途；不得为单一小功能引入重量级框架。
8. 禁止提交 `dist/`、`node_modules/`、真实 `.env`、未脱敏经营数据及测试生成物。
9. 每个模块完成后必须报告：修改文件、旧新行为对照、测试结果、视觉证据、未覆盖风险。
10. 未收到“提交”或“部署”的明确指令，不执行 Git 提交、推送或服务器变更。

## 12. 验收与上线门槛

每一模块必须通过以下四层检查：

```text
类型与静态检查
  + 纯业务逻辑测试
  + 浏览器真实行为测试
  + 桌面与手机视觉回归
```

业务重构必须使用脱敏固定数据，对比旧版与新版的采购金额、库存结存、销售成本、利润表与报表关键数字。存在不一致时，不得进入下一模块。

正式上线前必须验证：

- 登录、游客限制、退出和刷新恢复；
- 日报、采购、费用、库存、报损的新增、修改、删除、取消；

## 13. 实施前置阶段

2. 建立脱敏固定测试数据与旧版计算结果基线。
