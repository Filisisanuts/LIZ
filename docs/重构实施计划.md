## 一、总体策略

### 核心原则

1. **渐进式迁移**：不一次性重写，按功能域逐步替换
2. **新旧并行**：旧系统持续运行，新模块逐个上线
3. **每模块独立验收**：类型检查 + 业务逻辑测试 + 视觉回归
4. **可回滚**：保留旧代码，出问题 30 秒回退

### 迁移顺序依据

- 只读页面优先（低风险，建立基线）
- 简单表单次之（验证 CRUD + Repository 模式）
- 复杂业务最后（Purchase/Inventory 高风险）
- 基础设施收尾（Auth/Sync/Settings）

## 八、阶段 6：分享报表与部署

**目标**：服务器 API 鉴权，Nginx 部署

### 6.1 分享报表 API

```
server/
├── src/
│   ├── index.ts
│   ├── routes/
│   │   └── share-report.ts
│   └── services/
│       ├── report-share.ts
│       └── supabase-admin.ts
└── systemd/
    └── ax-coffee-report-api.service
```

API 流程：
```
GET /api/share-report/:token
  → 计算 token_hash
  → 校验有效性
  → 读取 Supabase 报表数据
  → 返回只读 DTO
```

### 6.2 Nginx 配置

```nginx
server {
    listen 80;
    server_name example.com;

    # 静态前端
    location / {
        root /var/www/ax-coffee/current;
        try_files $uri $uri/ /index.html;
    }

    # 分享 API
    location /api/ {
        proxy_pass http://127.0.0.1:3001;
    }
}
```

### 6.3 部署流程

```bash
# 1. 构建
npm run build

# 2. 上传到 releases 目录
rsync -avz dist/ server:/var/www/ax-coffee/releases/v1.0.0/

# 3. 原子切换
ssh server "ln -sfn /var/www/ax-coffee/releases/v1.0.0 /var/www/ax-coffee/current"

# 4. Nginx reload
ssh server "sudo nginx -t && sudo systemctl reload nginx"
```

## 十、风险与回滚

### 风险清单

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 数据计算不一致 | 报表数字错误 | 脱敏数据对比，四层验收 |
| 旧功能回归 | 用户无法使用 | 保留旧入口，30 秒回退 |
| 样式偏差 | 视觉不一致 | 视觉回归测试 |
| 移动端兼容 | 手机无法使用 | 5 视口验收 |

### 回滚流程

1. 修改软链接指向旧版本
2. Nginx reload
3. 验证旧版本正常
4. 分析失败原因
